B4.1 PRACTICAL EXTENSION: ADD A NEW BILL AND A NEW PAYER
--------------------------------------------------------
The existing Bill, OutPatient and InPatient classes do not need to be edited.
Add a new derived bill type, EmergencyBill, and a new payer implementation,
CorporatePayer. A payer is modelled as a separate policy interface so payer
rules are independent of bill calculation.

Save as b4.cpp:
#include <iostream>
#include <memory>
#include <string>
#include <vector>
#include <stdexcept>

class Bill {
protected:
    std::string patient;
public:
    explicit Bill(std::string p) : patient(std::move(p)) {}
    virtual ~Bill() = default;
    virtual double total() const = 0;
    virtual std::string type() const = 0;
    const std::string& name() const { return patient; }
};

class OutPatient : public Bill {
    double consultation, tests;
public:
    OutPatient(std::string p, double c, double t)
        : Bill(std::move(p)), consultation(c), tests(t) {}
    double total() const override { return consultation + tests; }
    std::string type() const override { return "OP"; }
};

class InPatient : public Bill {
    int days; double rate, surgery;
public:
    InPatient(std::string p, int d, double r, double s)
        : Bill(std::move(p)), days(d), rate(r), surgery(s) {}
    double total() const override { return days * rate + surgery; }
    std::string type() const override { return "IP"; }
};

// Extension 1: new bill type; existing bill classes are unchanged.
class EmergencyBill : public Bill {
    double emergencyFee, medicines;
public:
    EmergencyBill(std::string p, double e, double m)
        : Bill(std::move(p)), emergencyFee(e), medicines(m) {}
    double total() const override { return emergencyFee + medicines; }
    std::string type() const override { return "ER"; }
};

class Payer {
public:
    virtual ~Payer() = default;
    virtual std::string name() const = 0;
    virtual double pay(double billAmount) const = 0;
};

class SelfPay : public Payer {
public:
    std::string name() const override { return "SelfPay"; }
    double pay(double x) const override { return x; }
};

class InsurancePayer : public Payer {
    double cover;
public:
    explicit InsurancePayer(double c) : cover(c) {}
    std::string name() const override { return "Insurance"; }
    double pay(double x) const override { return x < cover ? x : cover; }
};

// Extension 2: new payer; existing payer classes are unchanged.
class CorporatePayer : public Payer {
    double discountRate;
public:
    explicit CorporatePayer(double d) : discountRate(d) {
        if (d < 0 || d > 1) throw std::invalid_argument("bad discount");
    }
    std::string name() const override { return "Corporate"; }
    double pay(double x) const override { return x * (1.0 - discountRate); }
};

int main() {
    std::vector<std::unique_ptr<Bill>> bills;
    bills.push_back(std::make_unique<OutPatient>("Ravi", 500, 1200));
    bills.push_back(std::make_unique<InPatient>("Meena", 3, 2500, 40000));
    bills.push_back(std::make_unique<EmergencyBill>("Arun", 8000, 2500));

    SelfPay self;
    InsurancePayer insurance(45000);
    CorporatePayer corporate(0.10);

    const Payer* payers[] = {&self, &insurance, &corporate};
    for (const auto& b : bills) {
        std::cout << b->type() << ' ' << b->name()
                  << " bill=" << b->total() << '\n';
        for (const Payer* p : payers)
            std::cout << "  " << p->name() << " pays "
                      << p->pay(b->total()) << '\n';
    }
}

Expected output:
OP Ravi bill=1700
  SelfPay pays 1700
  Insurance pays 1700
  Corporate pays 1530
IP Meena bill=47500
  SelfPay pays 47500
  Insurance pays 45000
  Corporate pays 42750
ER Arun bill=10500
  SelfPay pays 10500
  Insurance pays 10500
  Corporate pays 9450

The insurance payer pays the lesser of bill amount and cover. CorporatePayer
applies a 10% discount. These are illustrative policies; real payer contracts
must define co-pay, exclusions, taxes and rounding rules.

B4.3 PRODUCTION DECISION
------------------------
A polymorphic design is suitable for a hospital group with 15 hospitals,
two new bill types and three new payers per year, and 200,000 bills per day,
provided it is paired with RAII, validation, logging, tests and monitoring.
New bill types and payer policies can be added as new classes without changing
the established classes or central processing loop. This reduces regression
risk compared with repeatedly editing a large switch statement.

The B3 sample benchmark showed virtual dispatch slower than switch/variant in
that microbenchmark (about 65.7 ms versus 40.7/40.8 ms for 10 million bills).
At 200,000 bills/day, this difference alone is unlikely to outweigh the
maintenance benefit, but production throughput, concurrency, database access,
network calls and audit requirements must be measured end-to-end. Exceptions
should handle exceptional failures, not routine claim rejection. Use explicit
result/optional values for common business outcomes.

ALTERNATIVE: CONFIGURATION / PLUG-IN RULES
------------------------------------------
If bill and payer rules are data-driven, define validated configuration records:
- bill code, charge components, multipliers and fixed fees;
- payer code, coverage limit, discount/co-pay and exclusions;
- rule version, effective date and audit metadata.

Load and validate the rules at startup (or through a controlled versioned
refresh), then interpret the selected rule for each bill. Rule interpretation
usually requires a lookup plus a small number of arithmetic operations. A
virtual call is generally a direct indirect dispatch, while interpreted rules
may need map lookup and rule evaluation; cache compiled/normalized rules to
reduce repeated parsing. Rule storage is proportional to the number of rules,
O(R), and each bill requires its data plus a rule identifier. A class-based
design stores executable logic in code and typically has little per-bill rule
storage.

Configuration makes rate changes and simple new packages faster and may allow
business staff to update approved rules without a C++ release. It also creates
risks: malformed or conflicting rules, unsafe expression languages, versioning,
cache invalidation and auditability. Complex workflows may still need a new
class or plug-in. Use a restricted declarative rule schema, strict validation,
signatures/approval, immutable versions and rollback. Do not execute arbitrary
code from configuration files.

FINAL RECOMMENDATION
--------------------
Use polymorphic bill and payer interfaces for genuinely different behaviours,
smart pointers for ownership, and typed exceptions for exceptional technical
failures. Represent frequent business rejections with explicit result values.
Move rates and simple payer limits into versioned, validated configuration.
This hybrid provides extensibility, resource safety and operational control.
