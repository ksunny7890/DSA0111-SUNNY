COMPLETED CLAIM CODE
--------------------
Save as b2.cpp:
#include <iostream>
#include <stdexcept>

class ClaimError : public std::runtime_error {
public:
    using std::runtime_error::runtime_error;
};

double approve(double billed, double cover) {
    if (billed < 0 || cover < 0)
        throw std::invalid_argument("negative amount");
    if (billed > cover)
        throw ClaimError("exceeds cover");
    return billed;
}

double settle(double billed, double cover) {
    try {
        return approve(billed, cover);
    } catch (const ClaimError& e) {
        std::cout << "audit: " << e.what() << '\n';
        throw;                 // rethrow SAME active exception
    }
}

int main() {
    double cases[][2] = {{40000, 50000}, {60000, 50000}, {-1, 50000}};
    for (auto& c : cases) {
        try {
            double paid = settle(c[0], c[1]);
            std::cout << "approved " << paid << '\n';
        } catch (const ClaimError& e) {
            std::cout << "claim rejected: " << e.what() << '\n';
        } catch (const std::exception& e) {
            std::cout << "error: " << e.what() << '\n';
        }
    }
}

Compile and run:
g++ -std=c++17 -Wall -Wextra -pedantic b2.cpp -o b2
./b2

WHY EACH HANDLER RUNS
---------------------
- 40,000 <= 50,000: no exception; claim is approved.
- 60,000 > 50,000: approve throws ClaimError. settle catches ClaimError, audits
  it, and uses throw; to rethrow. main catches ClaimError.
- billed=-1: approve throws invalid_argument. settle catches only ClaimError,
  so it propagates to main's std::exception handler.

throw; VERSUS throw e;
---------------------
throw; rethrows the currently handled exception without creating a new exception
object and preserves its dynamic type.
throw e; throws a copy whose static type is the declared type of e. If e is a
base-class reference to a derived exception, this can slice off the derived part.
In this exact code e has type const ClaimError&, so throw e makes a ClaimError
copy and does not slice ClaimError to runtime_error. Nevertheless, throw; is the
preferred rethrow form because it preserves the original exception object.

ENGINEERED ERROR TESTS
---------------------
1. Negative charge: reject before calculation with invalid_argument.
2. Claim above cover: throw ClaimError; the audit handler records it and rethrows.
3. Unknown package code: use a lookup function and throw
   std::invalid_argument("unknown package code") if the code is absent.
4. Text where a number is expected: std::stod("abc") throws
   std::invalid_argument. Catch it at the input boundary and report invalid input.
5. Huge allocation: for example, try { std::vector<int> v;
   v.resize(v.max_size()); } catch (const std::bad_alloc& e) { ... }.
   This is platform-dependent: max_size may cause length_error before bad_alloc,
   and the OS may overcommit memory. A deterministic test can use a deliberately
   small allocation limit in a test allocator. Do not rely on crashing the machine.

TOP-LEVEL CATCH AND RESOURCE CLEANUP
------------------------------------
Use RAII so stack objects and smart pointers are destroyed during stack unwinding.
Example:
#include <iostream>
#include <memory>
#include <stdexcept>
struct Record {
    ~Record() { std::cout << "Record destroyed\n"; }
};
int main() {
    try {
        auto p = std::make_unique<Record>();
        throw std::runtime_error("test failure");
    } catch (...) {
        std::cout << "top-level: recovered\n";
    }
    std::cout << "program continues\n";
}
Expected:
Record destroyed
top-level: recovered
program continues
catch(...) catches any exception type, but should be a final safety boundary.
It cannot recover from every failure (for example, process termination or some
fatal memory exhaustion). Raw resources need RAII wrappers; destructors should
not throw.

EXCEPTION DESIGN EVALUATION
---------------------------
The tests show that exceptions separate normal billing logic from exceptional
conditions, typed handlers allow different responses, and throw; preserves the
original exception. Validation at the input boundary prevents malformed data
from reaching calculations. RAII ensures cleanup during stack unwinding.
Do not use exceptions for ordinary expected outcomes if invalid claims are common.

ALTERNATIVE: std::optional<double>
----------------------------------
Return std::optional<double>: return billed for a valid claim and std::nullopt
for a rejected claim. The caller checks has_value(). This avoids exception
construction and stack unwinding for routine rejections. A separate error code
or result type is needed if the caller must know WHY the claim was rejected.

Complexity for 1,000,000 claims:
- Both approaches perform O(N) validation, hence O(1) work per claim on average.
- Return/optional approach has predictable low cost whether 0%, 1%, or 50% fail.
- Exception approach is usually similar when no exception is thrown, but each
  thrown/caught exception is much more expensive. Cost rises sharply as the
  invalid percentage increases.
- optional stores a value plus a presence indicator; typically a small fixed
  per-result overhead (exact sizeof is implementation-dependent). Exception
  objects use runtime-managed storage only when thrown; do not store one object
  per successful result.
The actual timing depends on compiler, standard library and hardware.
